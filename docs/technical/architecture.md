# 技术架构文档 v0.1

## 1. 架构目标

本项目是一个「轻量级视频会议助手」网页应用。

第一版目标不是替代腾讯会议、飞书会议或 Zoom，而是在视频会议旁边提供一个 AI 工作台，帮助用户完成：

1. 会前准备。
2. 会中问答和讨论链路捕捉。
3. 会后跟进。
4. 下次会议自动带入历史上下文。

技术架构需要优先支撑这条主链路：

```text
会后跟进数据
  -> 生成下次会前准备
  -> 会中补充内容/问答/讨论链路
  -> 生成会后跟进草稿
  -> 用户确认
  -> 成为新的会后跟进数据
```

第一版优先保证会前准备和会后跟进闭环可靠。会中问答和讨论链路是增强体验，转写只是输入能力。

## 2. 技术选型

### 项目形态

采用 monorepo，前后端分离，但放在同一个项目文件夹中。

```text
会议助手/
  apps/
    web/
    api/
  packages/
    shared/
  docs/
    superpowers/specs/
    technical/
```

### 前端

- React
- Vite
- TypeScript

前端负责页面、交互、录音、文本编辑、AI 草稿展示和用户确认。

前端视觉和页面信息架构以 `stitch_` 原型为准，采用企业协作系统风格：

- 左侧固定导航：会议议题、我的待办、设置。
- 浅灰画布 + 白色内容卡片。
- 蓝色作为主操作、选中态和焦点态。
- 高密度信息布局，优先保证会议内容、待办和决策可扫读。
- Logo、侧边栏、顶部搜索、账号区域在所有业务页面保持一致。

原型中的“会议议题”是用户界面文案，在后端和数据模型中仍对应 `MeetingThread`。

### 后端

- NestJS
- TypeScript

后端负责账号壳子、数据权限、业务规则、AI 调用、转写调用和结构化结果保存。

### 数据库

- PostgreSQL
- Prisma

PostgreSQL 负责保存用户、会议线程、单次会议、会前准备快照、待办、工作进展、决策、风险、遗留问题、讨论链路、助手消息和会后草稿。

为了支撑原型中的实时记录页和全量记录页，数据库还需要保存逐条转写片段。第一版可以使用独立 `TranscriptSegment` 表，也可以先使用 `MeetingSession.transcriptSegments` JSON 字段；若需要编辑单条发言、搜索和导出，优先使用独立表。

Prisma 负责数据库模型定义、迁移和类型安全的数据访问。

### 认证

第一版采用演示级账号壳子：

- 用户输入 `entryName` 进入系统。
- 若账号不存在则自动创建。
- 若账号存在则直接进入。
- 后端返回 token。
- 后续请求通过 `Authorization: Bearer <token>` 鉴权。

第一版不做邮箱、手机号、密码、验证码、密码找回、第三方登录或企业单点登录。

### 大模型

大模型通过后端统一封装，不允许前端直接调用。

第一版使用 OpenAI-compatible API：

```text
LLM_BASE_URL=https://api.2006038.xyz/v1
LLM_MODEL=gpt-5.5
LLM_API_KEY=从环境变量读取
```

`LLM_API_KEY` 不允许写入代码仓库或文档正文。

设置页可以展示模型供应状态、当前模型名、Base URL 是否已配置和连接测试结果，但不能让前端输入、读取或保存 `LLM_API_KEY`。

### 转写

转写是辅助输入能力，不是主链路。

前端负责录音，后端负责接收音频并调用转写服务。转写失败时，用户仍可手动输入或粘贴会议内容。

第一版不要求会议平台级实时字幕，但前端实时记录页需要能展示本地录音过程中的转写片段或用户手动追加的发言片段。转写服务返回整段文本时，后端应至少生成一个默认转写片段。

## 3. 系统分层

```text
前端 Web
  -> 后端 REST API
    -> 业务模块
      -> AiModule
      -> TranscriptionModule
      -> Prisma/PostgreSQL
```

### 前端 Web

职责：

- 展示进入工作台页。
- 展示会议议题列表页，业务上对应会议线程列表。
- 展示会议线程详情和会前简报。
- 创建和编辑单次会议。
- 输入/粘贴会议内容。
- 录音并上传音频。
- 展示实时转写片段。
- 向助手提问。
- 展示 AI 生成状态。
- 展示会议综述、讨论链路、全量记录和会后跟进草稿。
- 展示会议待办和“我的待办”聚合视图。
- 展示模型服务配置状态和连接测试结果。
- 让用户编辑并确认正式记录。

前端不负责：

- 直接调用大模型。
- 直接调用转写供应商。
- 决定数据归属。
- 信任或提交 `userId`。
- 接触、展示或保存模型 API Key。

### 后端 API

职责：

- 解析 token，识别当前用户。
- 校验数据归属。
- 提供 REST API。
- 编排会前准备、会中问答、讨论链路、会后跟进。
- 调用 AiModule 和 TranscriptionModule。
- 保存正式数据。

### 数据库

职责：

- 持久化所有业务数据。
- 通过 `userId` 实现账号数据隔离。
- 支持软删除会议线程。

### AiModule

职责：

- 构造当前用户可访问的会议上下文。
- 按任务生成 prompt。
- 调用大模型。
- 要求并解析结构化 JSON 输出。
- 对 AI 输出做基础校验。

AiModule 是后端内部能力，不直接作为产品 API 暴露。

### TranscriptionModule

职责：

- 接收音频文件。
- 调用语音转文字服务。
- 返回转写文本。
- 生成或保存转写片段。
- 失败时返回可理解错误，不阻断主流程。

### SettingsModule

职责：

- 返回模型服务配置状态。
- 发起后端侧连接测试。
- 隐藏敏感配置值。

SettingsModule 不保存前端提交的模型 API Key。第一版模型配置仍来自部署环境变量。

## 4. 后端模块划分

### AuthModule

负责演示账号进入、退出和当前用户信息。

核心能力：

- 输入 `entryName` 进入系统。
- 自动创建不存在的账号。
- 返回 token。
- 解析当前用户。

### ThreadsModule

负责会议线程。

核心能力：

- 创建会议线程。
- 查询会议线程列表。
- 查询会议线程详情。
- 编辑会议线程。
- 软删除会议线程。

前端可以把会议线程展示为“会议议题”，但 API 和内部模块名称继续使用 Threads。

### PreparationModule

负责会前准备卡。

核心能力：

- 从历史决策、待办、工作进展、遗留问题、风险和下次带入项生成会前准备。
- 生成本次建议关注点和建议议程。
- 创建单次会议时，为会议保存会前准备快照。

### SessionsModule

负责单次会议生命周期。

核心能力：

- 创建单次会议。
- 保存会议内容。
- 保存和更新逐条转写片段。
- 更新会议状态。
- 保存会前准备快照。
- 用户确认正式会议记录。
- 允许 finalized 后继续编辑。

### AssistantModule

负责会中助手问答。

核心能力：

- 接收用户问题。
- 获取当前会议和会议线程历史上下文。
- 调用 AiModule 回答问题。
- 保存用户消息和助手回复。
- 返回回答来源。

### DiscussionModule

负责讨论链路。

核心能力：

- 从会议内容中抽取讨论链路。
- 结构化为议题、背景/事实、观点、分歧、结论、待确认问题和后续动作。

### FollowUpsModule

负责会后跟进。

核心能力：

- 生成会后跟进草稿。
- 保存草稿。
- 用户确认后拆分为正式数据。
- 管理待办、风险、遗留问题和下次带入项。
- 支撑会议待办页和“我的待办”聚合视图。

### ProgressModule

负责工作进展。

核心能力：

- 用户补充工作进展。
- 会后草稿生成工作进展候选。
- 工作进展进入下次会前准备。

### TranscriptionModule

负责录音转写。

核心能力：

- 接收音频文件。
- 返回转写文本。
- 返回或生成转写片段。
- 转写失败时允许用户继续手动输入。

### SettingsModule

负责模型配置状态展示。

核心能力：

- 读取后端环境变量配置状态。
- 返回脱敏后的模型供应信息。
- 提供连接测试接口。
- 保证前端不能读取或提交 `LLM_API_KEY`。

### AiModule

负责统一大模型接入。

核心能力：

- `ContextBuilder`：构造会议上下文。
- `PromptBuilder`：构造任务 prompt。
- `LlmProvider`：调用 OpenAI-compatible API。
- `StructuredOutputParser`：解析结构化输出。
- `Guardrails`：限制上下文、输入长度和输出结构。

## 5. 关键设计原则

### 产品接口使用业务语义

接口应使用会前准备、会中问答、讨论链路、会后跟进等业务语义。

推荐：

```text
GET  /api/v1/threads/:threadId/preparation
POST /api/v1/sessions/:sessionId/assistant/ask
POST /api/v1/sessions/:sessionId/discussion-chains/extract
POST /api/v1/sessions/:sessionId/follow-up-draft
POST /api/v1/sessions/:sessionId/finalize
```

不推荐把产品接口直接设计成暴露底层技术动作的名称，例如只表达“调用 AI”，却看不出业务目标是什么。

### AI 只生成候选，用户确认后才正式保存

AI 可以生成会前建议、助手回答、讨论链路候选和会后草稿。

会后跟进草稿必须经过用户确认，才能拆分保存为正式决策、待办、风险、遗留问题、工作进展和下次带入项。

### 会前准备动态生成，单次会议保存快照

打开会议线程时，系统动态生成最新会前准备。

创建单次会议时，系统将当时的会前准备保存为 `carryInSnapshot`。这样既能保证会前准备最新，也能在之后追溯当时会议基于什么上下文展开。

### 数据权限以后端为准

前端不能传 `userId` 决定数据归属。

后端必须从 token 中解析当前用户，并在所有业务查询中校验 `userId`。

### 前端原型优先但不突破安全边界

`stitch_` 原型决定页面结构、视觉层级和主要交互入口。若原型与安全或数据隔离规则冲突，以后端安全边界为准。

典型例子：

- 原型设置页中的 API Key 输入框应改为“后端已配置/未配置”的状态展示。
- 原型中的演示人物、部门和日期不能作为跨账号共享数据。
- 原型中的“本地浏览器数据”提示应改为演示账号提示。
